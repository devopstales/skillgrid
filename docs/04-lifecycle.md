# Lifecycle

A skill is alive: it is used, it rots, it is archived. A library of skills without lifecycle data is a museum — every skill looks equally current forever, and the catalog bloats until the description index no longer helps the agent trigger the right one.

This document explains the lifecycle model: provenance, adjacency, usage telemetry, and curation transitions. The full specification lives in `skill-creator/references/skill-lifecycle.md`.

## Provenance

Every skill records who made it in `metadata.created_by`:

| Value | Meaning | Curation scope |
|---|---|---|
| `human` (default) | Hand-written, curated | Off-limits for auto-archive; human edits or deletes deliberately |
| `agent` | Generated by the agent in a session | Eligible for stale → archive transitions on the curation interval |
| (absent) | Treated as human (conservative default) | Same as `human` |

The curation loop must not delete what a human wrote. A curator that touches a hand-written skill on a stale-usage signal is a curator that surprises its owner. When porting a skill from another system, keep the upstream provenance in `based_on` — attribution is what makes a port auditable.

## Adjacency

`related_skills` in `metadata` names the skills that compose with this one. The adjacency is a pointer, not a restatement:

- **Name only, no restatement.** The *why* of the composition lives in the skill's own prose, never duplicated into the list.
- **Forward-looking, unidirectional in form.** List the skills you call or that call you. Do not require the target to reciprocate.
- **Curate the graph with the skill.** When a skill is renamed, removed, or re-scoped, sweep `related_skills` entries that pointed at it. A stale adjacency is a router that lies.
- **Do not over-link.** `related_skills` is for *composition* (A feeds B, B gates A), not topical similarity.

The current composition graph (15 edges across 16 skills) is documented in `02-pipeline.md`.

## Usage Telemetry

A library-level `.usage.json` records, per skill:

| Field | Meaning |
|---|---|
| `use_count` | Times the skill was loaded into an agent context |
| `view_count` | Times it was read without triggering (browsed) |
| `patch_count` | Times its SKILL.md was edited |
| `last_activity_at` | Timestamp of the most recent load or patch |
| `state` | `active` \| `stale` \| `archived` |
| `pinned` | Boolean, exempt from all auto-transitions |

The harness writes `use_count` / `last_activity_at` when it loads a skill; the curation pass reads them. **The skill itself does not write its own telemetry** — that would be self-grading. Telemetry is an external signal about the library, not a field the skill maintains.

Skillgrid does not ship a curator daemon. The sidecar is *optional* and the format is the contract. If the library has no harness writing the sidecar, `last_activity_at` is the only honest field (update it on patch), and the stale/archive transitions below are manual.

## Curation Transitions

The lifecycle moves a skill through states. **The maximum destructive action is archive, never delete.**

| Transition | Signal | Applies to | Guard |
|---|---|---|---|
| `active` → `stale` | `last_activity_at` older than `stale_after_days` (default 90) | agent-created only | pinned skills exempt |
| `stale` → `archived` | `stale` for longer than `archive_after_days` (default 180) | agent-created only | pinned skills exempt; backup first |
| `archived` → `active` | human restores, or re-use detected | any | bump `last_activity_at` |

**Before any archive: a backup.** A tar.gz (or git tag) of the skill directory taken immediately before the transition, so rollback is one step. This is the invariant that makes "never delete" honest.

**Pinned skills are exempt from every auto-transition and every review pass.** Pinning is the owner's explicit "keep this even if it looks dead" signal — a skill that is rarely used but load-bearing (a setup skill, a safety skill) is pinned, not deleted.

## The Curation Interval

When the library grows past what a human reviews in one sitting (rule of thumb: > 30 skills, or a single review takes > 30 minutes), the curation becomes a scheduled pass:

1. **Status.** List every skill with its `state`, `last_activity_at`, `use_count`, provenance. The stale candidates jump out.
2. **Review candidates.** For each `active` skill that crossed the stale threshold and is agent-created, decide: still needed (bump or pin), genuinely dead (→ `stale`), or superseded (→ `archived`, name the replacement in `related_skills`).
3. **Backup, then transition.** Tar.gz, then move the state.
4. **Report.** One line per transition: skill, from→to, reason, backup path.

The interval is deliberate (weekly/monthly), not a background daemon. A daemon that archives skills while you work is a curator that surprises you; a scheduled pass you trigger is one you can watch.

## Lifecycle Red Flags

Observable signs the lifecycle is being violated:

- A skill with `created_by: agent` but no `last_activity_at` ever set (never used since creation — the RED eval never went GREEN)
- `related_skills` naming a skill that no longer exists
- An agent-created skill with 0 `use_count` that is not pinned and not archived (the curator never ran, or the skill is a zombie)
- A hand-written skill that the curation pass is about to auto-archive (provenance was not recorded — the curator is about to surprise its owner)
- An archive without a recorded backup path

## Size Budget

Every skill has a byte-size ceiling. The budget is tracked in `_shared/skill-size-budget.json`:

| Tier | Ceiling | Examples |
|---|---|---|
| standard | 22,000 bytes | most skills |
| large | 38,000 bytes | skills with heavy reference material |
| xl | 40,000 bytes | top-of-large skills |
| external | 90,000 bytes | skill-creator (meta-skill) |

The check is mechanical: `node .agents/skills/skill-creator/scripts/skill-size-budget.mjs check .` exits 0 when all skills are within ceiling. A silent overage is a drift signal — the skill grew without a deliberate re-tier.

## Frontmatter Validation

The frontmatter contract is mechanical: `node .agents/skills/skill-creator/scripts/check-frontmatter.mjs check .` exits 0 when all skills conform. The contract enforces:

- Field set and order: `name`, `description`, `license`, `metadata`
- `name` == directory name (kebab-case)
- `description` ≤ 1024 chars
- `metadata.version` is quoted `MAJOR.MINOR`
- `metadata.part-of: skillgrid`
- `metadata.created_by` and `metadata.related_skills` present (lifecycle fields)

## Audit

Before a skill ships (or after a significant edit), the 10-rule audit runs. The audit covers the four authoring phases (Trigger, Structure, Steering, Pruning) plus cross-cutting concerns. Findings are reported as a table: Rule / Status (PASS/WARN/FAIL) / Finding / Fix.

The full audit checklist is in `skill-creator/references/ten-rule-audit.md`.
