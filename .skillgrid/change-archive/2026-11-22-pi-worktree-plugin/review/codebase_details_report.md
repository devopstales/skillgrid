## Findings

### 1. Blocker — `repoRoot` is attributed to a snippet that does not exist in the contract

**Affected Scope:** `blueprint.md` line 291 (Task 2 Produces) and line 101 (threat matrix "Git repository selection" row).

**Discrepancy Description & Rationale:** Task 2's Produces declares `repoRoot(cwd: string): Promise<string>` as "the contract's existing `--show-toplevel` snippet". The contract (`.agents/skills/_shared/work-unit-commits/README.md`, § Worktree root + detection) contains no `--show-toplevel` snippet and no `repoRoot` — its "shared snippet" is the `GIT_DIR`/`GIT_COMMON` pair via `git rev-parse --git-dir` / `--git-common-dir`, whose stated purpose is *linked-worktree vs. submodule detection*, not cwd→toplevel resolution. The cited source does not exist in the referenced codebase. This matters operationally, not cosmetically: a plain `git rev-parse --show-toplevel` called from the primary checkout returns the **primary checkout's** toplevel, not the current worktree's. That would be wrong for the plugin's central scenario — the whole design rationale is "each worktree checkpoints its own turn, `pruneOtherSessions` runs per worktree at `session_start` (Task 5 Step 3: `pruneOtherSessions(repoRoot(ctx.cwd), …)`), and checkpoints are refused cross-worktree by branch name". The same defect also voids the threat-matrix test the blueprint claims to plan: "`repoRoot` from a worktree subdirectory resolves to the worktree toplevel (pass)" — a toplevel-only implementation cannot pass that test when `root` is the primary checkout. Task 2's implementation step (line 362) also specifies no `repoRoot` body at all, so the executor has no worktree-correct recipe. Note the blueprint elsewhere already knows the worktree-vs-submodule distinction is real (the contract's submodule guard is cited at line 291 as provenance, and R3-F005's rewrite of the same threat-matrix row introduced this exact citation). Fix: make the provenance the contract's `GIT_DIR`/`GIT_COMMON` snippet (worktree-aware by construction, submodule-safe via `--show-superproject-working-tree`), or specify `repoRoot` as `rev-parse --show-toplevel` **plus** the `GIT_COMMON != GIT_DIR → pwd` worktree override, and state both in Task 2 Step 3 where the implementation is written.

### 2. Major — Task 4's second prune test contradicts the liveness-aware spec and its own Step 3 code

**Affected Scope:** `blueprint.md` lines 489–498 (test "pruneOtherSessions removes other sessions' refs, keeps the current one") vs. lines 500–527 (liveness test) and the Step 3 implementation (lines 560–575: `PRUNE_MIN_AGE_MS = 3600 * 1000`, delete only refs with `now - created > PRUNE_MIN_AGE_MS`).

**Discrepancy Description & Rationale:** The test captures session `"old"`'s ref with a real clock a few milliseconds before calling `pruneOtherSessions(repo, "cur")` (default `now`), and expects `n === 1`. With the declared threshold, a <1-hour-old "other session" ref is **kept**, so the test as written fails — and the blueprint's own Step 4 line reads "Expected: PASS (13 tests total: capture 4 + restore 5 + prune 4)", i.e. this test is expected green. (The third, liveness test in the same group does use an injected `now` exactly because fresh refs survive — the second test simply forgot the same treatment.) This is the class of defect the pipeline has already caught twice (R2-F007, R4-F002: stale test expectations): the executor's `bun test` in Step 4 will fail on a test whose "Expected" line says PASS. Fix: inject a clock into that test (e.g. `pruneOtherSessions(repo, "cur", new Date(Date.now() + 2 * 3600 * 1000))`) or construct the ref with a backdated `created` value, so the assertion matches the liveness-aware rule.

### 3. Major — Task 2's "full metadata" test asserts a field name the contract's metadata block does not define

**Affected Scope:** `blueprint.md` lines 312–320 (test "mutating turn creates exactly one ref with full metadata", the `"untracked ["` assertion) vs. `work-unit-commits/README.md` § Scratch checkpoints Storage bullet.

**Discrepancy Description & Rationale:** The contract defines the ref-message metadata as: `branch`, `head`, `index-tree`, `worktree-tree`, `session`, `turn`, `label`, `created`, `preexisting-untracked` (plus, per R2/R5, the large-file/dir skip lists). The test's expected substring list asserts `untracked [` as a ninth field. No bare `untracked:` field is in the contract's block — the pre-existing-untracked list is named `preexisting-untracked`. The blueprint's own MH-1 states the metadata block as "branch, head, index-tree, worktree-tree, session, turn, label, created, untracked, largeFiles, largeDirs" (loosely matching pi-rewind's field names per findings R3), so the test was written against MH-1's informal list rather than the contract. Either way the plan currently ships one canonical metadata field name in MH-1, a different one in the test, and a third in the contract — and the contract-drift guard (R13) compares constants, not message field names, so nothing in the plan catches the third one. For a document whose stated goal is "documentation matches the actual codebase implementation exactly", a test that pins a field name the contract does not contain is a self-inflicted spec drift: the executor will implement `untracked` (test green), the contract says `preexisting-untracked`, and every later reader of the ref message parses the wrong key. Fix: assert the contract's field names (`preexisting-untracked`) in the test, or amend MH-1 + the Task 2/3 `Checkpoint` prose to one name and state it against the contract explicitly.

### 4. Major — Task 2's capture comment names a filter the contract requires and the test group never verifies

**Affected Scope:** `blueprint.md` lines 364–369 (capture comment step 2: "filtered untracked+modified via `git status --porcelain=v1 -uall` → apply IGNORED_DIRS (any path component), MAX_UNTRACKED_FILE_SIZE, MAX_UNTRACKED_DIR_FILES") vs. `work-unit-commits/README.md` § Scratch checkpoints Filtering ("**`.gitignore`'d paths**, plus the dir-name set …").

**Discrepancy Description & Rationale:** The contract's filter has two halves: `.gitignore`'d paths are never snapshotted, *plus* the dir-name set. The blueprint's implementation comment enumerates only the dir-name/size/file-count filters; `.gitignore`'d paths appear nowhere in the Task 2/3/4 test groups (the threat matrix's "Filesystem boundaries" row tests only the `.worktree/` case). A plain `git status --porcelain=v1 -uall` lists `.gitignore`'d untracked paths as `!!` entries, which an executor following the comment could easily include (or drop with no test to catch it). If a captured tree contains gitignored files, the restore step's `read-tree --reset -u <worktreeTreeSha>` plus `safeClean` interacts with them in ways the contract explicitly excludes ("Never delete: ignored dirs …" relies on them never being in the snapshot). The test group has a "capture leaves the real index byte-identical" test but no "gitignored untracked file is absent from the captured tree" test. Fix: add the `.gitignore` filter to the step-2 comment (or state the porcelain `!!` handling explicitly) and add one RED test asserting a `.gitignore`'d untracked file is not in the snapshot tree.

### 5. Nit — The "git fallback" citation points to the wrong sub-step

**Affected Scope:** `blueprint.md` line 112 (Global Constraints, `wt` requirement: absence → "git fallback applies (skill Step 0c)") and Task 11 Step 1 (the `README.md` Tool Dependency line: "optional — the git fallback path is unchanged without it").

**Discrepancy Description & Rationale:** In `execute/SKILL.md`, Step 0b is "Create via the tooling tier", where Tier 3 — `git worktree add` — is the git fallback; Step 0c is the *submodule guard / detected-worktree* step (per the same file's own cross-references, "in 0c, create worktrees on per-agent branches (0c's `git worktree add …`…)" and the `0a'` override text "skip 0a–0c"). The fallback a reader needs when `wt` is absent is Tier 3 of **0b**. The in-repo `README.md` line that Task 11 installs currently cites "execute Step 0b tier 1/2" for the plugin's role (correct) and "the git fallback path" unnamed (safe); the Global Constraints citation "skill Step 0c" is the one that is wrong. Fix: change the citation to `execute` Step 0b Tier 3 (or just "Step 0b" to match the existing README line).

### 6. Nit — Task 5 Step 3 calls `repoRoot` synchronously where the plan defines it as async

**Affected Scope:** `blueprint.md` line 291 (Produces: `repoRoot(cwd: string): Promise<string>`) vs. lines 659, 669, 673, 676 (`createCheckpoint({ root: repoRoot(ctx.cwd), …})`, `pruneOtherSessions(repoRoot(ctx.cwd), …)` ×2 — none `await`ed).

**Discrepancy Description & Rationale:** `repoRoot` is declared to return `Promise<string>` but every call site in Task 5's shape code passes its result by value without `await`, so `root` would be a Promise (the git spawn would fail or receive a `[object Promise]` cwd). This is shape code (the plan marks Task 5 as smoke-verified, and the ledger's R3-F018 class covers mechanical wiring nits), so it will be caught by `pi -e` in Step 4 — but the blueprint is the executor's only spec, and a declared-async symbol used synchronously in the same document is an internal contradiction a reader must resolve by guessing. Fix: either `await repoRoot(ctx.cwd)` at the four call sites or declare `repoRoot` synchronous; a single `git -C cwd rev-parse` spawn is trivially async, so the former is the consistent choice.
