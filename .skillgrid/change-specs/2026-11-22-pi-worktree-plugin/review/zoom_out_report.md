Part 2 (read-only) the harness cannot mechanically enforce — I enforced it by discipline: only `read`/`find`/`grep`/`glob` and two `mkdir`/`cat` writes for this report file (plus a local scratch note), no edits to the target. Part 3 (no project instructions) is enforced by this brief being my entire context — I did not read AGENTS.md/CLAUDE.md/rules files; the work-unit-commits README entered via the explicit reading list.

**Overall:** The blueprint is unusually disciplined for this altitude — it reuses both upstreams by mechanics rather than forking, keeps the skill deltas explicit (three one-way-door decisions, a named invariant list), and every module has a deletion test. Most of what I checked out (constants dedup, `git()` single seam, the 150ms bench as a must-have, core purity via import scan) is already the laziest working choice. The findings below are the real weeds I could still pull.

---

**Severity:** Major
**Affected Scope:** Task 3 (scratch-core restore) — the `restoreCheckpoint` signature, its Step 3 code, and the "Key links" bullet on the pair check.
**Simplicity Rationale:** The "second half of the pair" — worktree-root mismatch (OD-2) — is a redundant guard, not an atomic pair. A branch name exists in exactly one worktree of a repository at a time: two live worktrees can never share a branch, so `curBranch !== cp.branch` already implies worktree-root mismatch in every case that matters. The only way to reach the `worktree`-half refusal is a cross-clone case (different repo, same branch) where the checkpoint ref can't even be read — `loadCheckpoint` runs first and returns null ("no checkpoint"), so that path never produces a branch-refusal to fall through to the root check. The contract's fan-out guarantee (5 worktrees × 5 branches, refs never cross) holds on the branch half alone: each worktree's refs live in that worktree's branch. Cost: a `worktreeRoot` parameter threaded through a 3-argument signature, two `realpathSync` calls, a named refusal reason, a dedicated test group (the clone-based "refused: worktree-root mismatch" test), a whole one-way-door decision (OD-2), and the "Key links" warning about passing the session cwd or the check being "vacuous". A second refusal reason also doubles the refusal surface the restore dialog and `references/scratch-restore.md` must document. The branch check is the load-bearing invariant; the root half is belt-and-suspenders over a case git already makes unreachable. Drop OD-2 (keep the branch half, keep `worktreeRoot` out of the signature) and the "atomic pair" becomes "checkpoint records branch; restore verifies branch" — which is exactly what the contract's never-cross guarantee needs.

**Severity:** Major
**Affected Scope:** Task 6 (wt-core invariants) — `verifyStandardRoot`; Global Constraints "Standard root"; Task 7 Step 3 (recovery, "prefer the default branch's worktree").
**Simplicity Rationale:** Two altitude drops that read like inherited plumbing rather than designed behavior. (1) `verifyStandardRoot` reads worktrunk's effective path template (project `.config/wt.toml`, else user config) and verifies it lands worktrees under `<projectroot>/.worktree/`. But the skill tier says the template is *configured* (`worktree-path = "{{ repo_path }}/.worktree/{{ branch | sanitize }}"` is a user-config item the owner sets up per R4/findings R4), and the contract says worktrunk worktrees land in the standard root *by configuration* — the plugin doesn't create them via git fallback. Verifying an owner-set config string is checking something outside the plugin's trust boundary: the observed-template parse + drift-report + "never silently followed" machinery is a full invariant (MH-9, R7, a test group) that enforces a *config value* the skills already state in prose. The contract's real need is that the *plugin's own* actions (recovery targets, directive validation, marker state) address worktrees by a path it computed — and it does, via the recorded-worktree list. The template check should at most be a one-line "observed root differs from `.worktree/` — noted in the report" at first use, not a startup verification with a drift-reporting contract. (2) Recovery's "prefer the default branch's worktree" re-introduces a notion the rest of the design deliberately avoids: the whole skill system (execute Step 0b) exists because the default branch is *wrong* as a base for feature work, yet recovery's preference rule bakes the default-branch assumption back into the runner. Recovering to "the worktree whose branch matches the session's last recorded branch, else main, else any survivor" is the rule the session already knows; "prefer the default branch" is a heuristic imported from pi-worktrunk that the skillgrid deltas never asked for.

**Severity:** Major
**Affected Scope:** Task 8 (markers + dual-plugin warning) — `detectForeignMarkerPlugin`, the "Markers" Global Constraint, MH-13, Task 8 Step 1 test ("foreign plugin file present → warning fires").
**Simplicity Rationale:** `detectForeignMarkerPlugin` scans for the presence of worktrunk's own Pi plugin's extension file at `session_start` and warns if both are installed. That is a filesystem probe of *another package's install layout* — a coupling the plugin repo will own and maintain against someone else's file naming, for a conflict that the README already resolves ("uninstall worktrunk's Pi plugin"). The briefing's own disposition for the 🟡 shootdown was accepted-with-note: README note. The blueprint upgraded a one-line README instruction into a runtime detection function, a `session_start` hook, a warning string, and a test asserting "foreign plugin file present → warning fires". Detection of a foreign plugin by file scan is exactly the class of heuristic that rots when that plugin renames its extension file; the cost of the rot (duplicate markers) is cosmetic and already named in the README. Ship the README note and the "pi-worktree is the marker writer" warning on install; drop the detector and its test. If the dual-install actually shows up in the wild, a user-reportable conflict is a one-line changelog fix.

**Severity:** Major
**Affected Scope:** File Structure — `references/wt-commands.md` ("generated compact command catalog"); `scripts/make-catalog.ts`; the `catalog` npm script; Task 9 Step 4 ("`bun run bench && bun run catalog`"); Task 10 Step 1 ("`bun run catalog`" in the e2e).
**Simplicity Rationale:** A build-time generator (`make-catalog.ts`) that parses the installed `wt --help` output into a committed `references/wt-commands.md`, plus a `catalog` script wired into the e2e smoke — four artifacts serving the R1 pattern of "compact tool description + on-demand `--help`". But the R1 pattern *is* "help calls return immediately, matching the installed binary": the tool description says "run `wt <cmd> --help` for details" and the model gets the live catalog for free from the binary it's already running. The generated catalog is a *static copy* of a command whose surface changes per installed version — it goes stale between `wt` upgrades and needs the generator to stay honest, which is why the generator exists at all. That's two pieces of machinery (generator script + committed artifact + e2e step) to avoid a pattern that costs one sentence in the tool description. pi-worktrunk's "on-demand `--help`" means on-demand *from the binary*, not a regenerated snapshot. If a committed reference doc is wanted for humans, a hand-written one-page `references/wt-commands.md` that says "the catalog is `wt --help`" does the job; the generator and the e2e's `bun run catalog` step are weeds.

**Severity:** Nit
**Affected Scope:** Task 1 (scaffold) — `tsconfig.json`, `"devDependencies": { "bun-types": "latest", "typescript": "latest" }` in the package.json snippet, the import-scan test's top-of-file `readFileSync` imports.
**Simplicity Rationale:** Three small weeds. (1) `tsconfig.json` is created in Task 1 but no step ever uses it — bun runs TS directly (every test command is `bun test`/`bun run`); a tsconfig whose only consumer is a hypothetical future toolchain is YAGNI for a package whose manifest is a two-entry `pi.extensions` list. (2) `typescript: "latest"` as a devDependency for a repo that builds nothing (no `tsc` in any script) is a dependency that exists to be unused — drop it; `bun-types` is arguably the same but it at least types the `bun:test` imports. (3) The Task 1 test imports `readFileSync, readdirSync, statSync` but `statSync` is never used in the shown test — a dead import in the plan's own code that the executor will copy.

**Severity:** Nit
**Affected Scope:** Task 9 (contract-drift test) — the "extract the constant declarations from the § Scratch checkpoints + Tooling tiers prose (regex per constant…)" approach; Global Constraints "Constants are the contract's values, verbatim".
**Simplicity Rationale:** The drift guard greps a *prose* file with one regex per constant and fails with "contract shape changed — update the extractor" on no match. Parsing natural-language contract prose into typed constants with per-constant regexes is a parser that will break on the first innocuous rewording ("untracked files >10MiB" → "files over 10 MiB untracked") and require a code change to a *test* to fix. The contract file already states the constants in a compact block; the laziest drift guard is to make that block machine-readable (a fenced ` ```skillgrid-constants ` fence or a single JSON line in the contract) and have the test read one block instead of N regexes. That moves the drift surface from "N regexes that each need updating on reword" to "one fence the contract author keeps current" — and it's the same information, just formatted for the reader who already has to keep it accurate. If the fence feels like changing the contract's format, then the per-constant-regex version is acceptable — but the blueprint should name that tradeoff explicitly rather than shipping the regex-per-constant shape as if it were load-bearing.
