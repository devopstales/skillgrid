# Cross-Change Research Findings

Durable, still-relevant research findings carried forward across changes. Per-change research lives in `.skillgrid/specs/<topic>/findings.md` (archived with the change). `reflect` lifts the findings that outlive the change into this file, so they survive the archive.

**Rule:** a finding belongs here only if it constrains *future* changes — an external API fact, a version's behavior, a domain constraint, a library limitation. A finding that is only true for one change stays in that change's `findings.md`.

## Findings

- **Second brain / agent OS / Claude Code OS are three layers, not three alternatives.** (2026-09-30, second-brain-vs-agent-os research; constrains how all future ADRs + the glossary talk about mnemonic.) **Second brain = the ROLE** (a durable, offloaded store of your knowledge — tool-agnostic, Forte PARA/CODE lineage, Zettelkasten ancestor). **Agent OS = the RUNTIME** (an OS-like manager for an LLM agent: context paging, memory tiering, scheduling, storage, access control — MemGPT "LLMs as OS" arXiv:2310.08560, AIOS arXiv:2403.16971, MemoryOS arXiv:2506.06326). **Claude Code OS = a PRODUCT GENRE** (repos that treat Claude Code as an OS you configure: CLAUDE.md/AGENTS.md as boot config, markdown agents/skills as processes, hooks as interrupts, a markdown second brain as memory — code-os, agentic-os, claude-cortex, claude-agent-os; no single canonical product). Consequence for this project: **mnemonic is a second-brain ENGINE (the SQLite/FTS5 one) that plugs into an agent-OS-style runtime (OpenCode/Claude Code) in place of the markdown memory layer those OS repos ship.** It is the role-filler, a memory-driver in the runtime, and the memory-layer substitute in the genre — never "the agent OS" itself. ADR-0012 decided the *memory engine* (SQLite over llm-wiki markdown), not the role and not the runtime. Full sourcing: `.skillgrid/specs/2026-09-30-second-brain-vs-agent-os/findings.md`.

- **The `session_events` writer is multi-writer by design — scope every post-insert row reference to `(session_id, sequence)`, never "the latest."** (2026-10-01, session-events-layer retro; constrains any future code that writes or patches a `session_events` row or the `sessions` counters.) The events layer replaced a single-writer hub, so two commits/tool-calls can interleave in one session. `appendSessionEvent` returns the inserted `sequence`; any follow-up `UPDATE` (e.g. `RecordCommitEvent`'s payload write, `SessionSummary`'s `to_commit` stamp) must be `WHERE session_id=? AND sequence=?` and project-scoped — a `MAX(sequence)`/`DESC LIMIT 1` read-back crosses over under concurrency (the two IMPORTANT code-review findings fixed in `49ec4ce5`). Same-transaction `nextSequence` (max+1) + counter bump is the atomicity guarantee. Full sourcing: `.skillgrid/archive/2026-09-21-session-events-layer/report.md` (`## Retro` Decisions/Lessons; `## Re-verification`).
