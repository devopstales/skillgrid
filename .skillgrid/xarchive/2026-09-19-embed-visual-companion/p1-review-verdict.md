## Quality findings

**Important — re-answer no-op contradicts the blueprint threat matrix (controller to rule).** `decisions.go:207-210` (no-op early-return) + tests `decisions_test.go:502-512` (re-answer must NOT append a version) — **why it matters:** the blueprint threat matrix states a re-answer appends a version (2 `observation_versions` rows, latest content = second answer), the exact opposite of the no-op. Both cannot hold. **Assessment:** the implementer's reading (idempotent no-op, first answer kept, 1 version row) is internally consistent — `TestDecisionAnswerIdempotent` and `TestDecisionAnswerAppendsVersion` agree, and neither behavior violates "append-only history, never overwrites" (no-op: content untouched, 1 version; alternate: content advanced, 2 versions — both append-only). The flip side: if the threat-matrix reading is intended, `mem_governance` would show the second answer as the recoverable latest version; the no-op hides it. No other stated constraint breaks either way. Suggested fix: controller rules; if no-op stands, correct the blueprint threat-matrix line so it matches.

**Minor — answer 404 is shadowed by body-validation 400s.** `decisions.go:165-178` — **why it matters:** `handleDecisionAnswer` parses the id (400 if non-integer), decodes the body (400 if malformed), and requires `optionId` (400 if empty) *before* opening the handle / checking existence, so a non-existent id + empty `optionId` returns 400, not 404. The binding constraint "404 bad id" is met only for well-formed requests. Suggested fix: accept as-is (the tests use valid bodies, so the 404 path is verified), or reorder the existence check ahead of body validation.

**Minor — `visibility` is a coarser gate than the existing reader model, and the test proves only half of it.** `decisions.go:109` (`COALESCE(visibility,'') != 'private'`) — **why it matters:** the decisions inbox shows *every* non-private row regardless of reader/owner, whereas `visibilityFilter`/`canRead` (`governance.go:406-423,354-399`) also hide `restricted`/`agent` rows with no grant from a non-owner. So a `restricted` no-grant decision owned by someone else is listed to the dashboard. This matches the plan's team-scoped-reader model and the threat-matrix "Visibility gate" row, so it's acceptable — but `TestDecisionVisibilityGate` (`decisions_test.go:417-429`) only creates a `private` row, so it proves only the private-exclusion half; it never seeds a non-owner reader seeing a `restricted`-no-grant row. Suggested fix: (a) confirm the coarse gate is the intended dashboard scope, and (b) add a restricted-no-grant row to the visibility test to document the actual boundary.

**Minor — `UpdateContent` diverges from `mem_update`'s "append is best-effort" rule.** `governance.go:192-194` — **why it matters:** `Update` treats the version append as best-effort (`if appErr == nil { recorded }`, `timeline_update.go:88-90` — never blocks the update), but `UpdateContent` fails the whole answer if `AppendVersion` errors. Strictly safer (a version is guaranteed on every answer) but it is a behavioral divergence from the sibling path the constraint references. Suggested fix: fine to keep; note the divergence is intentional (a decision answer that loses its version would be worse).

**Minor — `normalized_hash` not recomputed on answer.** `governance.go:196-201` — **why it matters:** `mem_update` recomputes `normalized_hash` when content changes (`timeline_update.go:72`) to keep the 24h dedupe window correct; `UpdateContent` leaves the hash stale after the answer rewrite. Low practical impact for a decision row (the agent is unlikely to `mem_save` the same topic_key again post-answer). Suggested fix: recompute the hash from the new content, or document why a decision row's hash can stay stale.

**Minor (report accuracy) — "handoff hunks in both commits" is wrong.** report Concern #1 — **why it matters:** the RED commit contains no server.go change; only T02 carries the handoff + decision-registration hunks. No code impact, but the report overstates the RED pollution.
