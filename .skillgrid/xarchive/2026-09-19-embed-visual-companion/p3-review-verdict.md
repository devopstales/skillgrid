### Deviation assessment — inline iframe vs. reusing SandboxPreview

Implementer's claim: **accurate.** `SandboxPreview` (`skillgrid-ui/src/features/prototypes/SandboxPreview.tsx:15-35`) takes `{ html, device }` and renders `<iframe srcDoc={html} sandbox="allow-scripts">` inside a fixed device-width frame (1280/768/390, `maxWidth:100%`). It has **no `src` prop** — it inlines fetched HTML (its only consumer, the .stitch gallery, fetches via `GET /prototypes/{id}` then passes the body).

- (b) Sandbox contract is **identical on the security axis**: `sandbox="allow-scripts"` only, no `allow-same-origin`, `title` present (both have a11y title). SandboxPreview sets no `referrerPolicy` or other extra attrs, so nothing was dropped. Cosmetic deltas only: frame (device-width frame vs full-width 420px card container), `title` text (static vs dynamic), `bg-white`/`border-0` class details — all appropriate to the different contexts.
- (c) Reusing via a `src` extension is feasible but not zero: it would mean either adding an optional `src` prop + `!device` full-width mode to a component that currently always renders a device frame, or forking its frame markup — more surface than 5 lines of inline JSX. The brief's Interfaces section explicitly sanctioned "SandboxPreview **or a minimal inline `<iframe sandbox=\"allow-scripts\">`**" (`p3-brief.md:38`), and the blueprint's own Step 3 shows the inline form (`p3-brief.md:169-180`). The inline iframe is the lazier-correct choice. The only real cost is the sandbox string now existing in two files — see finding F1.

### 307-vs-400 mux nuance

Assessed. Go 1.22 `ServeMux` clean-path behavior does 307-redirect bare `..` segments before the handler; the redirect targets (`/secret.html`, `/a.html`) fall to the SPA fallback and 404 — never 200 — so no secret is served. The in-handler `prototypeFile` guard independently rejects the cleaned path anyway (defense in depth, same shape as `stitchFile`). Encoded forms (`%2e%2e/`, `%2F`) reach the handler and 400. The test table (`prototype_test.go:156-176`) asserts the **exact** per-case status (307/400) plus the no-leak invariant on every response (`rr.Code==200 && contains SECRET` → fail), and seeds an out-of-root `secret.html` for it. This is actually **stronger** than the brief's table (which wanted a blanket 400, including for bare `..` which is impossible at this route without an invented pre-check) and stronger than the Phase 7 `prototypes_test.go:84-96` threat loop, which only checks the invariant without exact status.
