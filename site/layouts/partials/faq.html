FAQ

Frequently asked questions

Do I have to run all 32?+
No. You run only the ones a change needs. A tiny change can be just execute and then verify. A bug is just structured-debugging.
What if there is no blueprint yet?+
Start at interviewing or brainstorming to resolve the design, then writing-blueprints. If a decision is still open when you'd build, the Owed-Decision Gate catches it — you resolve it, judge it not load-bearing, or record it as an Assumed blueprint that ships flagged until Ratify settles it.
Why clear the session between stages?+
So a fresh session reads from disk again. Every verb writes what it learned to files (glossary, ADRs, blueprint, acceptance, report), so the next agent starts from your project's actual state — not from a long, expensive, drifting chat.
Where do the files go if my docs/ folder is a published site?+
They don't have to. The spec zone lives wherever your tracker config points (Backlog.md by default, or gh/glab/jira). The repo-side artifacts live under .skillgrid/specs/, which is separate from any published docs/ tree.
Can I change the delivery style for one change?+
Yes. A Tier: line in the briefing overrides the project default per change. The tier selects which tail steps run; the change's shape still sets a floor the tier can't lower, and skipped steps are recorded as skipped, never silently absent.
Does this work on a team?+
Yes — that's the point. Everything lives in files in the repo, so a teammate who pulls the branch gets the same context, the same decisions, and the same open decision debt. ship checks your branch state before integrating and warns rather than charging ahead.
